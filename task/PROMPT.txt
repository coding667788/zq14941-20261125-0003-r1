我们要复核一批隔离设备导出的封存回执。请从空仓库做 counterweir，所有日志、摘要和设备都是合成的。每台设备每次启动都有一个明确的世代 ID。该世代实际序号是非负整数，日志只留下实际序号对 M 的余数，M 由输入声明。首尾允许有可信的实际序号锚点，两次已见事件之间可以漏掉记录或经过多圈。一个观察源有不可重排的采集次序，相邻已见事件的实际序号差有上下界；同一稳定事件 ID 在不同源出现时必须指向同一实际序号，余数相同的不同事件不能合并。同一世代不同事件的实际序号必须不同。同名设备按给定的生效映射认定，跨世代允许重置。
每台设备的保护批准与撤销按实际序号区间生效，批准绑定具体证物摘要。对每条待核回执，实现 audit CASE，分别输出可证实获批、可证实未获批、材料不足或证据互相矛盾。材料不足时给一条允许和一条拒绝的完整可复演序号分配。输出最早、最晚可能序号时，该上下界必须各自在满足所有源约束的某个完整分配中取得；矛盾时给能重放的最小证据集合，按条数及升序 ID 决胜。
再实现 repair CASE：从最多 16 条被标为可重新核实的观察中，选出暂停采信的条目，要求其余约束一致，所有强制回执仍可证实获批，所有标记为封存的回执在任何合法分配下均未获批。依次最小化核实成本、条数和升序 ID 列表。verify CASE RESULT 必须重新求解，拒绝只符合一边日志的见证、同成本但排序更后的方案以及把同一余数误当同一事件的结果。
给出能手算的两份夹具：其中一份用 M=4 展示区间内可跨两圈、合并两源后恰好排除一种分配；另一份展示移除单条可疑观察反而使强制回执由确定变成不确定。常规已对齐日志可达 20 万条，只有歧义组件需要精确求解，每个组件最多 16 个未确定事件。实际序号可到 10^12，不得逐序号或逐圈展开。Windows 普通 CPU，Python 3.12 标准库，交付 UTF-8 JSON CLI、README、合成夹具和小序号范围逐分配穷举的 unittest。
